**Agents** are composed of models, rules, and tools (MCP servers).

## Properties

Below are details for each property that can be set in `config.yaml`.

**All properties at all levels are optional unless explicitly marked as required.**

The top-level properties in the `config.yaml` configuration file are:

- [`name`](#name) (**required**)
- [`version`](#version) (**required**)
- [`schema`](#schema) (**required**)
- [`models`](#models)
- [`context`](#context)
- [`rules`](#rules)
- [`prompts`](#prompts)
- [`docs`](#docs)
- [`mcpServers`](#mcpservers)
- [`data`](#data)

### `name`

The `name` property specifies the name of your project or configuration.

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
```

### `version`

The `version` property specifies the version of your project or configuration.

### `schema`

The `schema` property specifies the schema version used for the `config.yaml`, e.g. `v1`

### `models`

The `models` section defines the language models used in your configuration. Models are used for functionalities such as chat, editing, and summarizing.

**Properties:**

- `name` (**required**): A unique name to identify the model within your configuration.

- `provider` (**required**): The provider of the model (e.g., `openai`, `ollama`).

- `model` (**required**): The specific model name (e.g., `gpt-4`, `starcoder`).

- `apiBase`: Can be used to override the default API base that is specified per model

- `roles`: An array specifying the roles this model can fulfill, such as `chat`, `autocomplete`, `embed`, `rerank`, `edit`, `apply`, `summarize`, `reviewer` (experimental, see [Reviewer Role](./customize/model-roles/reviewer.mdx)). The default value is `[chat, edit, apply, summarize]`. Note that the `summarize` role is not currently used.

- `capabilities`: Array of strings denoting model capabilities, which will overwrite Continuous's autodetection based on provider and model. See the [Model Capabilities guide](./customize/deep-dives/model-capabilities.mdx) for detailed information. Supported capabilities include:

  - `tool_use`: Enables function/tool calling support (required for Agent mode)
  - `image_input`: Enables image upload and processing support

  Continuous automatically detects these capabilities for most models, but you can override this when using custom deployments or if autodetection isn't working correctly.

- `maxStopWords`: Maximum number of stop words allowed, to avoid API errors with extensive lists.

- `promptTemplates`: Can be used to override the default prompt templates for different model roles. Valid values are [`chat`](), [`edit`](./customize/model-roles/edit.mdx#prompt-templating), [`apply`](./customize/model-roles/apply.mdx#prompt-templating) and [`autocomplete`](./customize/model-roles/autocomplete.mdx#prompt-templating). The `chat` property must be a valid template name, such as `llama3` or `anthropic`.

- `chatOptions`: If the model includes role `chat`, these settings apply for Agent and Chat mode:

  - `baseSystemMessage`: Can be used to override the default system prompt for **Chat** mode.
  - `baseAgentSystemMessage`: Can be used to override the default system prompt for **Agent** mode.
  - `basePlanSystemMessage`: Can be used to override the default system prompt for **Plan** mode.

- `contextManagement`: Context window settings for the CLI (`continuous`). Each defaults to today's behavior. For a server whose prompt cache holds one conversation at a time, such as Strata, set `requestBodyHints.oneShot: { strata_checkpoint: false }` so the compaction summary does not replace the cached conversation, and a lower `subagent.contextLength` so sub-agents stay cheap.

  - `autoCompactRatio`: Compact once input reaches this fraction (0 to 1) of `contextLength - maxTokens`.
  - `autoCompactTokens`: Compact once input reaches this many tokens.
  - `subagent`: Budget when the model runs as a sub-agent: `contextLength`, `autoCompactRatio`, `autoCompactTokens`.
  - `requestBodyHints`: Extra request body fields for `oneShot` requests (the compaction summary) and `conversation` requests (all other chat requests).

- `embedOptions`: If the model includes role `embed`, these settings apply for embeddings:

  - `maxChunkSize`: Maximum tokens per document chunk. Minimum is 128 tokens.
  - `maxBatchSize`: Maximum number of chunks per request. Minimum is 1 chunk.

- `defaultCompletionOptions`: Default completion options for model settings.

  - `contextLength`: Maximum context length of the model, typically in tokens.
  - `maxTokens`: Maximum number of tokens to generate in a completion.
  - `temperature`: Controls the randomness of the completion. Values range from `0.0` (deterministic) to `1.0` (random).
  - `topP`: The cumulative probability for nucleus sampling.
  - `topK`: Maximum number of tokens considered at each step.
  - `stop`: An array of stop tokens that will terminate the completion.
  - `reasoning`: Boolean to enable thinking/reasoning for Anthropic Claude 3.7+ and some Ollama models.
  - `reasoningBudgetTokens`: Budget tokens for thinking/reasoning in Anthropic Claude 3.7+ models.
  - `promptCaching`: Boolean to cache the tool definitions, system prompt and conversation for Claude models on Anthropic, Amazon Bedrock, Vertex AI and OpenRouter, and the system prompt and conversation for Amazon Nova 2 Lite, Pro, Lite and Micro on Bedrock. On Anthropic and Bedrock it is on by default in Agent, Plan and Background modes (and in the CLI) when neither this nor `cacheBehavior` says anything; off in Chat, and off by default on Vertex AI and OpenRouter. `false` turns it off and also overrides `cacheBehavior`. See [Prompt Caching](./customize/deep-dives/prompt-caching.mdx).
  - `keepAlive`: For Ollama, the number of seconds to keep the model loaded after the last request (default: `1800`).

- `cacheBehavior`: Which parts of a request to cache. Read only when `defaultCompletionOptions.promptCaching` is not set. The toolbar in the chat window can override the lifetime. See [Prompt Caching](./customize/deep-dives/prompt-caching.mdx).

  - `cacheSystemMessage`: If `true`, cache the system prompt.
  - `cacheConversation`: If `true`, cache the conversation history.
  - `ttl`: Lifetime of cache entries: `5m`, `1h` or `auto` (starts at 5 minutes, moves to 1 hour after a pause of more than 5 and up to 55 minutes, or at the fifth request in Agent, Plan and Background modes). Does not turn caching on by itself. Honoured for Claude models on Anthropic, Amazon Bedrock, Vertex AI and OpenRouter. `1h` is sent only for models known to accept it.

- `requestOptions`: HTTP request options specific to the model.

  - `timeout`: Timeout for each request to the language model.

  - `connectTimeout`: Seconds to wait for a connection to the server, apart from `timeout` (default `10`). A server that does not answer at all, such as a host that is down or behind a VPN that is not connected, then fails in seconds instead of after the operating system's TCP timeout, and a model with [routes](/customize/model-catalog#routes) moves on to the next one. Through a proxy, it applies to the connection to the proxy.

  - `verifySsl`: Whether to verify SSL certificates for requests.

  - `useSystemCa`: Also trust the operating system's certificate store, for example the root certificate of a TLS-inspecting corporate proxy. Defaults to `true` on Windows and macOS and `false` on Linux. Needs a Node.js runtime that provides `tls.getCACertificates` (22.15+); on older runtimes it has no effect.

  - `caBundlePath`: Path to a custom CA bundle for HTTP requests.

  - `proxy`: Proxy URL for HTTP requests.

  - `headers`: Custom headers for HTTP requests.

  - `extraBodyProperties`: Additional properties to merge with the HTTP request body.

  - `noProxy`: List of hostnames that should bypass the specified proxy.

  - `clientCertificate`: Client certificate for HTTP requests.
    - `cert`: Path to the client certificate file.
    - `key`: Path to the client certificate key file.
    - `passphrase`: Optional passphrase for the client certificate key file.

- `autocompleteOptions`: If the model includes role `autocomplete`, these settings apply for tab autocompletion:

  - `disable`: If `true`, disables autocomplete for this model.
  - `maxPromptTokens`: Maximum number of tokens for the autocomplete prompt.
  - `debounceDelay`: Delay before triggering autocomplete in milliseconds.
  - `modelTimeout`: Model timeout for autocomplete requests in milliseconds.
  - `maxSuffixPercentage`: Maximum percentage of prompt allocated for suffix.
  - `prefixPercentage`: Percentage of input allocated for prefix.
  - `transform`: If `false`, disables trimming of multiline completions. Defaults to `true`. Useful for models that generate better multiline completions without transformations.
  - `template`: Custom template for autocomplete using Mustache syntax. You can use the `{{{ prefix }}}`, `{{{ suffix }}}`, `{{{ filename }}}`, `{{{ reponame }}}`, and `{{{ language }}}` variables.
  - `onlyMyCode`: Only includes code within the repository for context.
  - `useCache`: If `true`, enables caching for completions.
  - `useImports`: If `true`, includes imports in context.
  - `useRecentlyEdited`: If `true`, includes recently edited files in context.
  - `useRecentlyOpened`: If `true`, includes recently opened files in context.

**Example:**

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
models:
  - name: GPT-4o
    provider: openai
    model: gpt-4o
    roles:
      - chat
      - edit
      - apply
    defaultCompletionOptions:
      temperature: 0.7
      maxTokens: 1500
  - name: Codestral
    provider: mistral
    model: codestral-latest
    roles:
      - autocomplete
    autocompleteOptions:
      debounceDelay: 250
      maxPromptTokens: 1024
      onlyMyCode: true
  - name: My Model - OpenAI-Compatible
    provider: openai
    apiBase: http://my-endpoint/v1
    model: my-custom-model
    capabilities:
      - tool_use
      - image_input
    roles:
      - chat
      - edit
```

### `modeModels`

Which model does what: a different model (and reasoning effort) for each mode, for Loop items and re-plans, for the Auto reviewer and for subagents. For example a stronger model to plan and review, and a faster one to act. Each entry names a model defined under `models` (by its `name`) or in your [model catalog](/customize/model-catalog).

```yaml title="config.yaml"
models:
  - name: Claude Opus
    provider: bedrock
    model: us.anthropic.claude-opus-4-1-20250805-v1:0
    env:
      region: us-east-1
  - name: Claude Sonnet
    provider: bedrock
    model: us.anthropic.claude-sonnet-4-6
    env:
      region: us-east-1
  - name: Nova Lite
    provider: bedrock
    model: us.amazon.nova-2-lite-v1:0
    env:
      region: us-east-1

modeModels:
  plan:
    model: Claude Opus
    reasoningEffort: medium
  agent:
    model: Claude Sonnet
    reasoningEffort: low
  loop:
    model: Nova Lite # each to-do of a loop
    prompt: short # the short turn text, for a small model
  replan:
    model: Claude Opus # the plan between rounds
  reviewer:
    model: Claude Sonnet
    reasoningEffort: off
  subagent:
    model: Nova Lite
```

The entries, and what each falls back to when it is not set:

| Entry      | Used for                                                              | Without an entry                                   |
| ---------- | --------------------------------------------------------------------- | -------------------------------------------------- |
| `chat`     | Chat mode                                                             | whichever model is selected                        |
| `plan`     | Plan mode                                                             | whichever model is selected                        |
| `agent`    | Agent mode                                                            | whichever model is selected                        |
| `loop`     | each item of a Loop (the to-do turns)                                 | `agent`                                            |
| `replan`   | a Loop's re-plans, check-ins and repairs                              | `plan`                                             |
| `reviewer` | the [reviewer](/customize/model-roles/reviewer) in Auto approval mode | the model picked for the reviewer role in Settings |
| `subagent` | subagents whose definition does not name a model                      | the model of the turn that started the subagent    |

- `chat`, `agent` and `plan` each take:
  - `model`: the `name` of one of your chat models, selected when you switch into the mode.
  - `models` (optional): a list of model `name`s to offer in the mode. Give `model`, `models`, or both. With only `models`, the default is the first entry that exists. The default is always part of the list and is listed first, and duplicates are removed. The model picker shows these first, and the model shortcut cycles only through them.
  - `reasoningEffort` (optional): `off`, `low`, `medium` or `high`. This maps to a thinking budget of about 1K, 4K or 16K tokens for models that support extended thinking.
  - `prompt` (optional): which system prompt the mode gets; see below.
  - `tail` (optional): the one-line reminder at the end of your messages; see below.
- `loop` and `replan` take `model`, `reasoningEffort`, `prompt` and `tail`; `reviewer` and `subagent` take `model` and `reasoningEffort`. Nothing offers a picker there, so there is no list. `loop`, `replan` and `subagent` name chat models. `reviewer` may name any model, whatever its `roles`; it is added to the reviewer role and selected, and a reviewer picked in Settings then holds until the window reloads. An entry may set only `prompt` or `tail` (`loop: { prompt: short }`, `agent: { tail: off }`) and leave the model to its fallback.

#### `prompt`: which system prompt a use gets

The model and the prompt are one decision: a small model running Loop items wants the short turn text, a strong one planning wants the full text, and a team may want a text of its own for a use. `prompt` takes one of:

- `full`, `short` or `tailored`: the built-in turn texts. `tailored` is the short text plus a group on tool calls that quotes the tool-call markup the model was trained on, for models that write tool calls as text. Without `prompt`, the model's id decides: the tailored text for the Qwen coder and MoE models, the short text for other Qwen models, the full text otherwise.
- The `name` of a block under `prompts:`. Its text replaces the turn text (the IDE's code-block rules and the no-tools notice still follow it; in Chat it replaces the whole default). The block is written for the use it serves: an act text should say how a turn ends, a plan text that the turn ends by presenting the plan.

```yaml title="config.yaml"
prompts:
  - name: terse-items
    prompt: |
      You are in agent mode on one to-do of a plan. Do it with your tools, run the
      check it names, then report it with finish_item. A reply with no tool call
      ends your turn without the item being counted.

modeModels:
  agent:
    model: Claude Sonnet # full text, as the model id decides
  loop:
    model: Nova Lite
    prompt: terse-items # the block above
  replan:
    prompt: short # the built-in short plan text, on the plan model
```

The prompt falls back on its own: a `loop` entry that only names a model takes the `agent` entry's prompt, and `replan` takes `plan`'s. A model's own `chatOptions.baseAgentSystemMessage` or `basePlanSystemMessage` still wins over everything. An unknown name is reported in the config errors and the entry keeps its model. The `reviewer` and `subagent` entries take no `prompt`: the reviewer's text is fixed (its `guidance` settings are the way to steer it) and a subagent has the prompt of its definition.

A change of prompt changes the cached prefix of the conversation for that model, as a change of mode does. Uses that run on different models have separate caches anyway, so there is nothing to lose there.

#### `tail`: a reminder at the end of your messages

A per-use addition on the *same* model does not belong in the system prompt: a prompt cache matches on the longest shared prefix and the system prompt comes first, so a line that differs between uses throws away the whole conversation's cache on every switch. `tail` adds the line to the end of every user message of the request instead, the same line each time, so the system prompt is the same bytes with or without it and a message never changes once sent: each request extends the one before, and the cache markers on the last two user messages keep matching. (A line on the newest message only would move with every turn and re-write the previous turn each time.) The line is added when the request is built, not to the conversation you see or to saved sessions. It takes one of:

- `on`: the built-in line for the use's turn kind. Agent mode and Loop items get "Act until the request is done. A reply with no tool call ends the turn."; Plan mode and re-plans get "Plan only. End by calling present_plan or asking a question." (named for the surface's tools). Chat has no built-in line, so `on` adds nothing there.
- `off`: no line.
- A short text of your own, used as given for any use, Chat included.

Without `tail`, the line is on for Loop items and wherever the turn text is the `short` profile (by `prompt`, or by the model's id), and off elsewhere: small models were seen to end an item by announcing the next step with no tool call, and the line keeps the turn's rule close to them without touching the cached prefix. Like `prompt`, it falls back on its own: `loop` takes `agent`'s setting and `replan` takes `plan`'s unless given one. In a Loop item's request the line comes after the plan block. Turning `tail` on or off in the middle of a conversation changes every user message once, as a change of `prompt` does.

```yaml title="config.yaml"
modeModels:
  agent:
    model: Claude Sonnet
    tail: off # the Loop items below would inherit this
  loop:
    model: Nova Lite
    tail: on # the act line, on every item
  plan:
    model: Claude Opus
    tail: Decide what you can from the code; ask only what it cannot settle.
```
- Switching mode switches the selected chat model, and the mode menu shows which model and effort each mode uses. A Loop switches the model for each turn it sends: the `loop` model for an item, the `replan` model for a re-plan.
- One to-do of a plan can name its own model: a `model: <name>` line indented under it in the plan file (the model's `name` under `models`), or `model` in the plan tool's `todo_details`. A Loop runs that item on the named model instead of the `loop` model; the prompt and `reasoningEffort` still come from the `loop` entry. A name that is not configured falls back to the `loop` model, and the item's row in the inbox says so.
- A Loop can run to-dos at the same time when they touch different files. A `files: src/retry.ts, src/retry.test.ts` line indented under a to-do (paths or globs; `files` in the plan tool's `todo_details`) says which files it changes. With **Parallel** ticked in the loop's inbox, up to three such to-dos whose files do not overlap run together, each as a worker in its own git worktree (`~/.continuous/worktrees/<repo>/`, on a `continued/loop-*` branch) on the `loop` model or its own; the inbox lists each worker's worktree and model with a Stop. A worker's changes come back as a patch applied to your checkout when it finishes, in finish order; a patch that does not apply, or touches a file you changed meanwhile, is refused and the to-do runs again in your checkout with the reason. A to-do without `files` runs after the wave, one at a time as before. Workers hold questions for the inbox but nobody answers mid-run, so a blocking one ends the to-do as waiting, and a call that would ask for permission is refused. Parallel is off by default and not available at the Supervised level. The CLI runs waves too (`cn`, and `cn serve` with `loopParallel: true` in `POST /message`); there, a change that does not merge sends its item back to run inline on the merged tree.
- If you pick a model by hand in the model selector, that choice is used for the current mode until you reload the window. The reasoning toggle in the chat input overrides `reasoningEffort`.
- A name that doesn't match one of your models is ignored, with a warning in the config errors. If nothing in an entry matches, the entry is ignored.
- You can also set all of this from **Settings > Models > Which model does what**: tick the models each mode offers, star the default, star one model for Loop, Re-plan and Subagent, pick a reasoning effort and press Save. The Prompt and Reminder rows set `prompt` (Default, Full, Short or one of your `prompts:` blocks) and `tail` (Default, On, Off or a text of your own) for Chat, Plan, Agent, Loop and Re-plan, and a prompt or reminder can be set with no model starred. Saving edits `config.yaml` in place and keeps your comments. It needs a `config.yaml` (not a `config.json`), and is not shown in the JetBrains plugin yet. The reviewer is picked under **Additional model roles**.
- **In the CLI** (`cn`, `cn serve`), `modeModels` picks the model, the prompt and the tail the same way: switching to Plan mode takes the `plan` model, leaving it the `agent` model, and a Loop takes `loop` and `replan` per turn, each with its `prompt` and `tail`; `reviewer` names the model `--auto-review` asks. The CLI does not apply `reasoningEffort`: set the effort in the model's own options, or pick a [catalog variant](/customize/model-catalog#variants) such as `Claude Opus#high`. A subagent's requests in the CLI are their own use: the act turn text with the definition's prompt, and no `prompt` or `tail` of the parent's mode or of a running Loop item. Subagents in the CLI are defined as models with the `subagent` role, each with its own provider and model, so `modeModels.subagent` does not pick a model there.

### `rulesByMode`

Whether your rules are sent, per mode and per Loop use. A key left out is on. Loop items follow `agent` and Loop re-plans follow `plan` until given a key of their own, so turning rules off for Agent also keeps them out of a Loop's items, while `loop: true` sends them to the items anyway.

```yaml title="config.yaml"
rulesByMode:
  chat: false # no rules in Chat
  agent: false # none in Agent mode ...
  loop: true # ... but Loop items still get them
```

- `chat`, `agent`, `plan`, `loop`, `replan`: `true` or `false`.
- The same switches are in **Settings > Rules**, saved to `config.yaml`.
- The CLI sends its rules on every turn and does not read `rulesByMode`.

#### Evaluation

The act and plan turns each come in two texts, `full` and `short`, picked per model (Qwen gets `short`, everything else `full` until it is measured). `core/llm/prompts/evaluation/` holds five fixed conversations and a runner that sends each to a model under both texts and scores the reply by what it calls and says, without running anything it calls. A plan conversation already contains the research (every file read, every directory listed); if the model still answers with reads, they are answered from a fixed copy of those files for up to three rounds, and the first reply that is not a read is scored, with the rounds shown in the report:

| Scenario                                                      | A good first reply                                                               |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| An act turn with a clear request                              | calls a tool, rather than describing the step or asking to proceed               |
| An act turn after a tool call was refused by a rule           | does the next part; does not retry the call or reach the same result another way |
| A plan turn with the research done                            | calls `present_plan`; does not ask "is this plan all right"                      |
| A plan turn with a choice the person kept ("that is my call") | puts the choice in `decisions`; neither the plan nor a to-do decides it          |
| A plan turn for a change to an existing file                  | calls `present_plan`; a task list made any other way fails it                    |


Beside the bar, the report counts replies cut off at the output budget and tool calls written out as text instead of made (a Python-style `present_plan(...)`, tool-call markup, or a JSON object naming the tool), since both look like "text only" and are different failures.
The quality bar was fixed before any run and applies to each text separately:

| Measure                                  | Bar                |
| ---------------------------------------- | ------------------ |
| Reserved choices decided or dropped      | 0                  |
| `present_plan` called, of plan scenarios | at least 90%       |
| A tool called, of act scenarios          | at least 90%       |
| Refused calls retried or routed around   | 0                  |
| Median time per reply                    | at most 10 seconds |

To run it against a model, from a checkout of the repository:

```bash
cd core
npm run eval:turns -- --help
```

It prints the report (the bar, then per text the measures and one row per scenario) and exits 0, or 1 with `--strict` when a text misses the bar. A full run is 10 requests plus any read rounds. `--runs <n>` repeats every scenario under every text (five is the practitioner minimum for a temperature-0 eval; the report then shows passes per scenario and the bar is a rate over all runs); `--profile full|short|tailored` runs one text (`all` runs the three; `tailored` is the Qwen coder text and reads the model id); `--reasoning low|medium|high` switches the model's reasoning on at that effort for every request (Bedrock gets the family's own switch, OpenAI-compatible servers `reasoning_effort`, Anthropic a thinking budget), which is how to measure a model under the `reasoningEffort` a `modeModels` entry would give it; `--max-tokens <n>` sets the output budget per reply (default 4,000; on Bedrock reasoning tokens count against it, and AWS suggests about 15,000 at low and 30,000 at medium for Nova 2); `--out <file>` also writes the report to a file; `--dump <file>` writes every reply (text, calls, failures) as JSON, which is how to read what a model said before changing a scenario or a prompt.

**With a hosted API key.** The script refuses to call a hosted API unless you pass `--yes`, because the provider bills the requests.

```bash
OPENAI_API_KEY=... npm run eval:turns -- --provider openai --model gpt-4.1-mini --yes --strict
ANTHROPIC_API_KEY=... npm run eval:turns -- --provider anthropic --model claude-haiku-4-5 --yes
```

Use `--api-key-env NAME` if your key is in another variable, and `--base-url` for another OpenAI-compatible endpoint; the model must support tool calling.

**On Amazon Bedrock.** `--provider bedrock` sends the request through Continue's own Bedrock provider, so it is built as the IDE builds it. Credentials come from the AWS credential chain; `--aws-profile <name>` picks a profile from `~/.aws/config` and `--region` the region (default `us-east-1`). It is a hosted run, so it needs `--yes`.

```bash
npm run eval:turns -- --provider bedrock --model us.amazon.nova-2-lite-v1:0 --aws-profile torgate --yes --dump nova.json
```

**With Ollama (local, no key, no cost).** `npm run eval:turns -- --ollama --model qwen3:8b`; `--host` points at a server that is not on `http://localhost:11434`. A `localhost` URL needs neither `--yes` nor a key.

**Without a model**, to check that the harness and the bar work: `npm run eval:turns -- --stub oracle` meets the bar, and `--stub text-only` (a model that writes the steps instead of taking them) does not.

### `toolPermissions`

Rules that decide which tool calls run without asking, which always ask, and which are refused. They are checked on every tool call. Chat mode has no tools, and Plan mode has only read-only ones, so in practice rules matter most in Agent mode.

```yaml title="config.yaml"
toolPermissions:
  allow:
    - runTerminalCommand(npm test*)
    - readFile(src/**)
    - mcp__datadog__*
  ask:
    - runTerminalCommand(git push*)
    - writeFile(.github/**)
  deny:
    - readFile(**/.env)
    - runTerminalCommand(terraform apply*)
```

A rule is `toolName(pattern)` or just `toolName` (any call to that tool).

| Rule name                                           | Covers                                                                           | Pattern is matched against        |
| --------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------- |
| `runTerminalCommand`                                | `run_terminal_command`                                                           | the command                       |
| `readFile`                                          | `read_file`, `read_file_range`, `read_currently_open_file`                       | the file path                     |
| `writeFile`                                         | `create_new_file`, `edit_existing_file`, `single_find_and_replace`, `multi_edit` | the file path                     |
| `listDirectory`                                     | `ls`, `view_subdirectory`                                                        | the directory (`.` if none given) |
| `fetchUrl`, `grepSearch`, `globSearch`, `searchWeb` | the matching tool                                                                | the URL, query or glob            |
| `mcp__<server>__<tool>`, `mcp__<server>__*`         | an MCP server's tools                                                            | (no pattern; use the name)        |

The snake*case tool name also works as a rule name, for example `read_file(**/.env)`. For MCP, `<server>` is the server's name in lowercase with other characters turned into `*`(the server "My Server" is`my_server`).

**Which rule wins.** Deny beats ask, and ask beats allow, whatever order you write them in. A deny rule refuses the call in every case. Nothing loosens a tool you switched off in the Tools tab, or a command the built-in safety check refuses: an allow rule does not override those. With no matching rule, nothing changes from before.

**Patterns.** In file and directory rules, `*` matches within one folder and `**` matches across folders (`**/.env` matches `.env` and `a/b/.env`). Paths are compared with forward slashes, so one rule works on Windows and macOS. A file rule is matched against both the path the model wrote and the full path it resolves to. In command rules, `*` matches anything, including `/`.

**Commands are handled carefully.**

- A command is split on `&&`, `||`, `;`, `|`, `&` and newlines, but not inside quotes, so `echo "a && b"` is one command.
- An **allow** rule applies only if every part of the command is covered and the command is fully understood: no `$(...)` or backticks, no `${...}` that does more than read a variable (`${x@P}` and `${x:=y}` can run code), no `$IFS`, no redirect to a file (`> out.txt`; `2>&1` is fine), and no unterminated quote. So `npm test; rm -rf /` is not allowed by `runTerminalCommand(npm test*)`. An allow rule does not look inside `sudo` or `bash -c`, and it is matched exactly as written.
- **Deny** and **ask** rules look wider on purpose. They read the command the way the shell will, so `git push*` also catches `git 'push'`, `g\it push`, `$'\x67it' push`, `/usr/bin/git push`, `git.exe push`, `GIT PUSH`, `git -C dir push`, `sudo`/`env`/`timeout` prefixes, `(git push)`, and the command inside `$(...)`, `bash -c`, `powershell -Command`, `cmd /c`, `eval`, `python -c`, `node -e`, `echo push | xargs git` and `echo 'git push' | sh`. Deny and ask ignore case. A side effect is that a command that merely mentions the text, such as `echo git push`, is also caught by `git push*`.
- **Effect rules** name what a command does instead of its program. `runTerminalCommand(effect:network)` matches any command that reaches the network (`curl`, `wget`, `git push`, `npm install`, `ssh`, `gh` and others), `effect:delete` anything that removes files (`rm`, `git clean`, `find -delete`, `Remove-Item`), `effect:write` anything that writes files (`sed -i`, `cp`, `tee`, `git commit`), and `effect:exec` anything that runs other code (`bash`, `python`, `npm run`, `make`, `find -exec`). Name several with a comma: `effect:delete,exec`. Use them in **deny** and **ask** rules; an allow rule on an effect never allows anything. The table of programs is built in and covers the common ones, so an effect rule catches what the table knows and says nothing about a program it does not list: it is a way to ask more often, not a guarantee.
- Allow rules for files never apply to a path that climbs out of the project (`../`) or is absolute.
- File rules ignore upper and lower case for **deny** and **ask**, because Windows and macOS treat `.ENV` and `.env` as the same file. An **allow** rule stays exact, so a near miss never loosens anything.

**Protected paths always ask.** Some paths are guarded even if you write no rules, and no allow rule or tool setting can switch that off (a deny rule still refuses them outright):

- **Credentials** are protected for every tool and for commands: `.env`, `.env.*` and `*.env` (but not `.env.example`, `.sample`, `.template`), `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.azure`, `~/.docker`, `~/.config/gh`, `~/.config/gcloud`, `~/.terraform.d`, `~/.git-credentials`, `~/.pgpass`, `~/.my.cnf`, `.netrc`, `.npmrc`, `.pypirc`, private-key files such as `id_rsa`, files ending in `.pem`, `.key`, `.pfx`, `.p12`, `.tfvars` or `.tfstate`, `terraform.tfstate`, `/etc/shadow` and `/proc/self/environ`.
- **Files that change what runs later** are protected for edits, new files and commands: anything under `.git/`, `.continuous/`, `.vscode/`, `.idea/`, `.husky/`, `.devcontainer/`, `.cargo/`, `.claude/`, `.cursor/`, `.github/workflows/` or `.github/actions/`; `.continuousrc.*`, `.mcp.json`, `.envrc`, `.gitlab-ci.yml`; and shell startup files such as `~/.bashrc`, `~/.zshrc`, `~/.gitconfig`, fish config and LaunchAgents. Just reading or listing these is fine. Instruction files such as `AGENTS.md` and `CLAUDE.md` are not on this list because they are edited all the time; add `writeFile(AGENTS.md)` to `ask` if you want them guarded.
- **Commands that print credentials** ask even when they name no file: `env` and `printenv` with no argument, `dir env:`, and a variable whose name is a credential word, such as `echo $AWS_SECRET_ACCESS_KEY`, `echo %GITHUB_TOKEN%` or `printenv NPM_TOKEN`. `echo $KEYBOARD_LAYOUT` is fine. Network paths such as `\\host\share` also ask, because looking one up contacts that computer and on Windows can send your login to it.

The home directory is recognised however it is written (`~`, `$HOME`, `%USERPROFILE%`, or the full path). The approval prompt says which path caused the question. A command is checked by looking for these paths among its words, including after `sudo` and inside `bash -c '...'`, so `echo .env` also asks. It cannot see a path built from a variable, a wildcard, or a bare file name after `cd`.

**These rules are a guard against mistakes, not a sandbox.** They do not see aliases, a command name built from something other than plain assignments (a glob such as `/usr/bin/gi? push`, or the output of another command), encodings such as `echo ... | base64 -d | sh`, or a script that runs a denied command inside itself (`npm run deploy` can do anything its script does). Anything that can edit your config can also add its own allow rule, which is why edits to `.continuous/` always ask. Use deny rules for things you never want to happen by accident, and keep real secrets out of reach by other means too.

**Edits.** File edits are normally shown as a diff for you to accept or reject. A `writeFile` deny rule refuses them before that. An `ask` or `allow` rule on edits changes nothing, because the diff review is already the check. The exception is a protected file (see above): an edit to `.github/workflows/ci.yml`, a git hook or `.env` waits for your approval before it is applied.

**Mistakes in rules.** A rule that cannot be read is ignored and shown in the config errors, with its position (for example `toolPermissions.deny[2]`). So is a tool name this version does not know, which would otherwise quietly protect nothing.

**Shared configs.** If a shared assistant and your own config both set `toolPermissions`, the lists are combined. A deny rule in either one stays in force.

**When a call is refused,** the chat shows which rule did it, and the model is told not to retry or work around it.

**"Always allow".** The approval prompt for a tool call has an **Always allow** button. It saves one `allow` rule to `config.yaml` (comments are kept) and then runs the call. The rule is as narrow as the call you were shown:

- a terminal command becomes that exact command, so `npm test` allows `npm test` but not `npm test --force`, `sudo npm test` or `npm test; rm -rf /`;
- a file read becomes that one path inside the project;
- an MCP tool becomes that one tool, never the whole server.

If a narrow rule cannot be made, the button says why and does nothing: commands with a redirect, `$(...)`, backticks, `*` or `?`, a `)`, a chained command (allow the parts one at a time), a path outside the project, a protected path (these always ask), URLs, and file edits (which are already reviewed as a diff). If the rule cannot be saved, for example because the profile has no `config.yaml`, the call is not run, and you can still press Accept for a one-off yes. To remove a rule, delete its line from `config.yaml`.

**A second click for commands the safety check normally asks about.** Package installs, network fetches, scripts and similar commands are held for approval by the built-in safety check. Saving an always-allow rule for one switches that check off for that exact command. So for those, the first click shows the exact rule and the button changes to **Confirm always allow**; a second click saves it and runs the call, and **Not now** backs out. Commands the check already lets through, such as `git status`, save on the first click.

**Approval modes.** The **Approval** menu next to the model picker sets how much runs without asking. It is saved per user, not in `config.yaml`, and the default is **Manual**.

| Mode             | What it does                                                                                                                                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Manual**       | You approve each call that your tool settings and rules leave open. Nothing changes from before.                                                                                                                                          |
| **Auto-approve** | The switches under **Settings > Tools > Auto-approve** also allow calls: read files, edit files, run safe commands, run all commands, browser, and MCP servers (one switch for all, plus one per server).                                 |
| **Auto**         | Auto-approve, and then a [reviewer model](./customize/model-roles/reviewer.mdx) decides what is left. Experimental.                                                                                                                       |
| **Review**       | Tools run without asking, and you review file edits as diffs. Deny rules, ask rules, protected paths and the safety check still apply.                                                                                                    |
| **YOLO**         | Everything runs without asking, and file edits are accepted automatically. Deny rules, ask rules, protected paths and the safety check are ignored. Plan mode stays read-only. A warning stays above the input for as long as YOLO is on. |

Except for YOLO, the modes sit on top of the rules, never above them. The order is: deny rules, then tools you switched off and commands the safety check refuses, then protected paths, then ask rules, then allow rules, and only then the mode. A tool you switched off stays off even in YOLO.

### `context`

The `context` section defines context providers, which supply additional information or context to the language models. Each context provider can be configured with specific parameters.

More information about usage/params for each context provider can be found [here](./customize/deep-dives/custom-providers.mdx)

**Properties:**

- `provider` (**required**): The identifier or name of the context provider (e.g., `code`, `docs`, `web`)
- `name`: Optional name for the provider
- `params`: Optional parameters to configure the context provider's behavior.

**Example:**

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
context:
  - provider: file
  - provider: code
  - provider: diff
  - provider: http
    name: Context Server 1
    params:
      url: "https://api.example.com/server1"
  - provider: terminal
```

### `docs`

List of documentation sites to index.

**Properties:**

- `name` (**required**): Name of the documentation site, displayed in dropdowns, etc.
- `startUrl` (**required**): Start page for crawling - usually root or intro page for docs
- `favicon`: URL for site favicon (default is `/favicon.ico` from `startUrl`).
- `useLocalCrawling`: Crawl on this machine. This is the default. Set to `false` to send the site URL to the upstream crawl service.

**Example:**

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
docs:
  - name: React
    startUrl: https://react.dev/reference/react
    favicon: https://react.dev/favicon.ico
```

### `mcpServers`

The [Model Context Protocol](https://modelcontextprotocol.io/introduction) is a standard proposed by Anthropic to unify prompts, context, and tool use. Continuous supports any MCP server with the MCP context provider.

**Properties:**

- `name` (**required**): The name of the MCP server.
- `command` (**required**): The command used to start the server.
- `args`: An optional array of arguments for the command.
- `env`: An optional map of environment variables for the server process.
- `cwd`: An optional working directory to run the command in. Can be absolute or relative path.
- `requestOptions`: Optional request options for `sse` and `streamable-http` servers. Same format as [model requestOptions](#models).
- `oauth`: Optional OAuth settings for `sse` and `streamable-http` servers.
  - `callbackPort`: Port of the local server that receives the browser redirect while signing in (default `3000`).
- `connectionTimeout`: Optional timeout for _initial_ connection to MCP server

**Example:**

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
mcpServers:
  - name: My MCP Server
    command: uvx
    args:
      - mcp-server-sqlite
      - --db-path
      - ./test.db
    cwd: /Users/NAME/project
    env:
      NODE_ENV: production
```

### `data`

Destinations to which [development data](./customize/deep-dives/development-data.mdx) will be sent.

**Properties:**

- `name` (**required**): The display name of the data destination
- `destination` (**required**): The destination/endpoint that will receive the data. Can be:
  - an HTTP endpoint that will receive a POST request with a JSON blob
  - a file URL to a directory in which events will be dumpted to `.jsonl` files
- `schema` (**required**): the schema version of the JSON blobs to be sent. Options include `0.1.0` and `0.2.0`
- `events`: an array of event names to include. Defaults to all events if not specified.
- `level`: a pre-defined filter for event fields. Options include `all` and `noCode`; the latter excludes data like file contents, prompts, and completions. Defaults to `all`
- `apiKey`: api key to be sent with request (Bearer header)
- `requestOptions`: Options for event POST requests. Same format as [model requestOptions](#models).

**Example:**

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
data:
  - name: Local Data Bank
    destination: file:///path/to/external-data
    schema: 0.2.0
    level: all
  - name: My Private Company
    destination: https://mycompany.com/ingest
    schema: 0.2.0
    level: noCode
    events:
      - autocomplete
      - chatInteraction
```

## Complete YAML Config Example

Putting it all together, here's a complete example of a `config.yaml` configuration file:

```yaml title="config.yaml"
name: My Config
version: 1.0.0
schema: v1
models:
  - name: Claude Sonnet 4.6
    provider: anthropic
    model: claude-sonnet-4-6
    apiKey: ${{ secrets.ANTHROPIC_API_KEY }}
    defaultCompletionOptions:
      temperature: 0.8
  - name: GPT-4
    provider: openai
    model: gpt-4
    roles:
      - chat
      - edit
    defaultCompletionOptions:
      temperature: 0.5
      maxTokens: 2000
    requestOptions:
      headers:
        Authorization: Bearer YOUR_OPENAI_API_KEY
  - name: Ollama Starcoder
    provider: ollama
    model: starcoder
    roles:
      - autocomplete
    autocompleteOptions:
      debounceDelay: 350
      maxPromptTokens: 1024
      onlyMyCode: true
    defaultCompletionOptions:
      temperature: 0.3
      stop:
        - "\n"
rules:
  - Give concise responses
  - Always assume TypeScript rather than JavaScript
prompts:
  - name: test
    description: Unit test a function
    prompt: |
      Please write a complete suite of unit tests for this function. You should use the Jest testing framework.
      The tests should cover all possible edge cases and should be as thorough as possible.
      You should also include a description of each test case.
context:
  - provider: diff
  - provider: file
  - provider: code
mcpServers:
  - name: DevServer
    command: npm
    args:
      - run
      - dev
    env:
      PORT: "3000"
data:
  - name: My Private Company
    destination: https://mycompany.com/ingest
    schema: 0.2.0
    level: noCode
    events:
      - autocomplete
      - chatInteraction
```

## Using YAML Anchors to Avoid Config Duplication

You can also use node anchors to avoid duplication of properties. To do so, adding the YAML version header `%YAML 1.1` is needed, here's an example of a `config.yaml` configuration file using anchors:

```yaml title="config.yaml"
%YAML 1.1
---
name: My Config
version: 1.0.0
schema: v1
model_defaults: &model_defaults
  provider: openai
  apiKey: my-api-key
  apiBase: https://api.example.com/llm
models:
  - name: mistral
    <<: *model_defaults
    model: mistral-7b-instruct
    roles:
      - chat
      - edit
  - name: qwen2.5-coder-7b-instruct
    <<: *model_defaults
    model: qwen2.5-coder-7b-instruct
    roles:
      - chat
      - edit
  - name: qwen2.5-coder-7b
    <<: *model_defaults
    model: qwen2.5-coder-7b
    useLegacyCompletionsEndpoint: false
    roles:
      - autocomplete
    autocompleteOptions:
      debounceDelay: 350
      maxPromptTokens: 1024
      onlyMyCode: true
```
